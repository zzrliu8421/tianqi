# SkyWeather 天气数据源准确性与可信度分析

> 整理自 2026-10-24 会话（DeepSeek Harness，session-35682fda）中关于"天气信息来源准度/可信度"的回答。
> 分析基于当时的工作区代码（数据层解析逻辑近期未改动）。
>
> **核心结论：数据源本身都是正规来源，没有"野数据"；但项目里有 4 个会系统性扭曲"准度"的实现问题——AQI 标准错位、跨时区时间错位、混合源不一致、定位与来源不可审计。也就是说，数据源可信 ≠ 你看到的值可信。**

## 1. 数据源清单与真实性质

| 用途 | 项目实际调用 | 数据性质 | 准度判断 |
|---|---|---|---|
| 中国大陆实况温度、天气现象、风力 | 高德 `v3/weather/weatherInfo?extensions=base` | 官方气象数据加工，**高德文档未披露数据源和更新频率**，只返回 `reporttime` | 较高，但**不可审计** |
| 24 小时、7 天预报 | 高德路径也用 **Open-Meteo**；或和风 `24h/7d` | 数值模式预报（多源模式混合，数公里至 11km 级），不是观测 | 中等：城市级可用，降水时段和极端天气偏差大 |
| AQI | **Open-Meteo air-quality 的 `us_aqi`**；和风源才是中国 AQI | 模式化大气成分（11km），**美国 EPA 标准** | **中低**（见下） |
| 日出日落 | Open-Meteo | 天文计算 | 可靠 |
| 紫外线、体感、能见度、气压 | Open-Meteo | 模式值 | 一般；UV 取的是"当日最大值" |
| 地理编码 | 高德、和风、Open-Meteo（GeoNames） | 地名库 | 中文地名高德最准；Open-Meteo 中文容易匹配错 |
| IP 定位 | 高德 `v3/ip`、IPnews、GeoDB、geolocation-db | IP 库或运营商注册地 | 城市级；VPN、移动网络、企业出口常错 |
| 公网 IP 探测 | Cloudflare trace、ipip、ipify | — | 只用来取 IP，不影响天气值 |

## 2. 四个系统性失真（带证据）

### ① AQI 标准错位——最严重，而且线上正在发生

- 代码取的是 `us_aqi`（[fetchOpenMeteoAQI](../index.html#L3757)、[mergeAQI](../index.html#L3830)），但等级阈值用的是**中国 AQI** 的 50/100/150/200/300（[getAQIInfo](../index.html#L3568)）。**数值是美国的尺子，标签用的是中国的尺子。**
- 同一 PM2.5 浓度下，US AQI 数值普遍比 CN AQI 高，套上中国等级会**高报 1–2 档**。举例（按 EPA 2024 与 HJ 633-2012 分段粗算）：
  - PM2.5 = 20 µg/m³ → 中国官方 AQI 约 29（优），US AQI 约 71（良）；
  - PM2.5 = 60 → 中国约 81（良），US 约 154（中度污染）。
  - 页面会显示"中度污染"。
- 线上站点 `QWEATHER_KEY=false`（查 `/api/status` 可见），所以**当前线上 AQI 全部是 US AQI 贴中国标签**。配了和风之后才会变成中国 AQI——同一张卡片标准会变。
- 还有两层：Open-Meteo 是 11km 模式，不是国控站实测；且只取了 PM2.5/PM10/NO₂/O₃，**没有 SO₂/CO**，而 README 写了 SO₂。
- 实测抓包：北京 `pm2_5=301.7`，但 `us_aqi=192`——说明 AQI 和展示的浓度**不是同一口径**（很可能一个用 24h 均值、一个用瞬时值），两者不能互相校验。

### ② 跨时区时间错位

- `timezone=auto` 返回的是**地点本地钟表时间，且不带时区偏移**。实测纽约返回 `current.time=2026-10-23T11:00`、`timezone=America/New_York`；而 `new Date("…T11:00")` 会按**浏览器本地时区**解析。
- 后果：在北京（23:06）查纽约，`t < now` 的过滤会把纽约当天剩余所有小时全部丢掉，24 小时列表从**次日 00:00** 开始。
- 昼夜主题用的是 `new Date().getHours()`（设备时间，[updateDayNight](../index.html#L2258)）：查纽约时按北京时间显示夜景。
- 日期和星期用 `new Date("2026-10-23")`（按 UTC 解析），负时区可能错一天。

### ③ 混合源不一致

- 中国路径 = 高德实况 + Open-Meteo 预报/AQI/体感/UV/动画。显示天气文案来自高德，动画类型却来自 Open-Meteo 的 `weatherCode`（[renderWeather](../index.html#L4889)）——可能出现"阴"的文案配下雨动画。
- 体感温度来自 Open-Meteo，温度来自高德，两者不同源，可能对不上。
- 页面徽章只显示 `_provider`（"高德地图"），不显示内部的 `source`（"高德地图 + Open-Meteo"），用户无法知道预报和 AQI 其实不是高德的。

### ④ 定位与"实时"的语义

- **没有 GPS**。README 写了 GPS，但代码里没有 `getCurrentPosition`，自动定位实际是 IP 定位。
- IP 定位是城市级；`_ipFetchDone` 把公网 IP 和网络类型**终身缓存**，换网络、挂 VPN 后不刷新。
- "实时天气"对 Open-Meteo 源其实是模式逐小时值，不是观测；高德实况才更接近观测。用户不知道当前显示的是哪种。

## 3. 这些源到底准不准？

- **没有任何免费源能保证城市级准确**。预报本身就有误差（温度 1–3°C、降水时段偏移是常态），这是行业共性，不是项目 bug。
- 中国大陆：实况 **高德 ≈ 和风 > Open-Meteo**；AQI **和风（CN 标准）> 官方国控站 > Open-Meteo（US 标准 + 模式）**；预报 高德/和风/Open-Meteo 差异取决于天气类型，不能一概而论。
- Open-Meteo 的强项是覆盖/免费/一致性，弱项是**中国本地化**（模式分辨率、AQI 标准、中文地名、时区）。当"全球兜底"用没问题，但作为中国区的**主数据**用，就需要标注清楚。

## 4. 5 分钟可自测的三件事

1. 同一时刻打开中国天气网/和风，对比本 App 的温度、天气现象、AQI 等级。
2. 搜"纽约"：看 24 小时列表是不是从明天 00:00 开始、背景是不是夜景、星期对不对。
3. 直接打开 `https://air-quality-api.open-meteo.com/v1/air-quality?latitude=39.9&longitude=116.4&current=us_aqi,pm2_5`，看数值与页面卡片是否一致。

## 5. 改进建议（按性价比排序）

1. **AQI 二选一**：要么用中国 AQI 自算（HJ 633-2012，取 PM2.5/PM10/NO₂/SO₂/O₃/CO 六项中的最大分指数），要么切和风；如果保留 `us_aqi`，UI 必须标"US AQI"，不能写中文"优/良"。
2. **时区**：用响应里的 `utc_offset_seconds` 做换算；过滤 24 小时用地点时间，昼夜主题也用地点时区。
3. **统一主源**：中国区要么全走高德（`extensions=all` 本来就有预报接口，现在只用了 `base`），要么全走 Open-Meteo；至少让动画/体感与文案同源。
4. **标注**：显示"来源 + 更新时间 + AQI 标准"，徽章显示完整 `source`；README 删掉 GPS、SO₂ 这类不实描述。
5. **定位**：给 IP 缓存加 TTL 或手动刷新，别终身缓存。

## 6. 对比赛（青创赛）的意义

这恰好是一个**现成的"数据可信度"章节**：报告里可以写"多源天气数据的一致性评估与展示口径修正"，用自己的 App 做对照实验（同一城市，高德 vs Open-Meteo vs 官方，温度/AQI/降水的一致性），这比空谈"用了多源"有说服力得多。

但注意：**没有真值就不要下"某源更准"的结论**，只做"与官方公开值的一致性分析"，并明确误差来源（标准不同、分辨率不同、更新时间不同）。
